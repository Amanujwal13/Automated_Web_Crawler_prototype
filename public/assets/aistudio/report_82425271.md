## 2. Critical Bugs (Must Fix)

### C1. `handleStartCrawl` double-fetches instead of reading POST response

**File**: `src/App.tsx` (lines 168-175)  
**Problem**: The `handleStartCrawl` function does a `POST` to `/api/crawl`, then calls `safeJsonFetch(res.url)` on the response URL — which performs a **second GET request** to the same endpoint. The POST response body is never read.

```tsx
// Current (broken):
const res = await fetch('/api/crawl', { method: 'POST', ... });
const data = await safeJsonFetch(res.url);  // re-fetches with GET, gets 404 JSON fallthrough

// Should be:
const res = await fetch('/api/crawl', { method: 'POST', ... });
const data = await res.json();
```

**Impact**: The crawl will start on the server, but the UI will never receive the success JSON — it may show a false error alert or silently swallow the response. Same bug exists in `handleResume` (lines 191-207).

---

### C2. `asyncio.run()` called inside a synchronous per-URL loop — breaks on repeated calls

**File**: `crawler/main.py` (line 61)  
**Problem**: `asyncio.run(fetch_html(url, config))` is called inside `_process_url`, which runs in a sequential `for` loop. `asyncio.run()` creates and destroys an event loop on **every URL**. While this technically works on CPython, it:

1. Has significant overhead (spawning a new event loop + Playwright browser per URL)
2. Can fail in environments where an event loop already exists (e.g., Jupyter, certain Windows setups)
3. On Python 3.10+, calling `asyncio.run()` from within an already-running loop raises `RuntimeError`

**Fix**: Create a single event loop at the top of `main()` and run all URLs through it, or use `asyncio.get_event_loop().run_until_complete()`.

---

### C3. `server.ts` hardcodes `python3` — does not exist on Windows

**File**: `server.ts` (lines 30, 138, 192)  
**Problem**: The server uses `spawn('python3', ...)` everywhere. On Windows, the Python executable is `python`, not `python3`. This means:

- `/api/runs` will 500 error (bridge fails)
- `/api/crawl` crawl never starts
- `/api/resume` resume never starts
- `/api/tests/run` tests never run

**Impact**: The entire web UI is non-functional on Windows unless you have `python3` aliased.

**Fix**: Use `process.platform === 'win32' ? 'python' : 'python3'` or detect via a config variable.

---

### C4. `robots.py` uses global module-level mutable cache — no thread safety, leaks across tests

**File**: `crawler/robots.py` (line 9)  
**Problem**: `_ROBOTS_CACHE` is a module-level mutable dictionary shared across all invocations. While the test file uses `clear_robots_cache()` in a fixture, this design:

1. **Leaks state** between separate test modules if pytest runs them in the same process
2. Is **not thread-safe** if the server were to handle concurrent requests
3. Caches `False` (disallowed) **permanently** — if a robots.txt fetch fails due to a transient network issue, that host is blocked forever for the entire process lifetime

**Fix**: Add TTL-based expiration to the cache, or pass cache as a parameter instead of using module-level state.

---

### C5. `store.py::get_connection()` runs `CREATE TABLE IF NOT EXISTS` on every single call

**File**: `crawler/store.py` (lines 30-36)  
**Problem**: Every function that calls `get_connection()` (which is every store function) re-runs the full schema DDL via `conn.executescript(SCHEMA)`. This means:

1. **Every `mark_done`, `mark_failed`, `mark_blocked`, `pending`, `records` call** opens a new connection AND runs two `CREATE TABLE IF NOT EXISTS` statements
2. On a 100-URL crawl, this results in ~300+ redundant DDL executions
3. No connection pooling or reuse

**Fix**: Initialize schema once (e.g., in a separate `init_db()` function called at startup), and either reuse connections or use a connection pool.

---

### C6. `main.py` creates run with `"temp_placeholder"` output directory, then updates it

**File**: `crawler/main.py` (lines 138-144)  
**Problem**: The run is created with `output_root / "temp_placeholder"` as the output dir, then immediately updated with the real path. This is a race condition if the process crashes between line 140 and 144 — the database will contain a run pointing to a `temp_placeholder` directory that does not exist.

```python
run_output_dir = config.output_root / "temp_placeholder"  # Placeholder
run_id = create_run(run_output_dir, db_path=db_path)
actual_output_dir = config.output_root / run_id
with get_connection(db_path) as conn:
    conn.execute("UPDATE runs SET output_dir = ? WHERE id = ?;", ...)
```

**Fix**: Generate the run_id first (via `generate_run_id()`), compute the actual output dir, then pass it directly to `create_run()`.

## 3. Security Issues

### S1. `server.ts` — No input sanitization on `runId` parameter (Path Traversal)

**File**: `server.ts` (lines 74-103)  
**Problem**: `req.params.id` is passed directly to Python bridge and filesystem paths with zero validation. A malicious `runId` like `../../etc/passwd` could:

1. In `GET /api/runs/:id/log` (line 85): Construct `path.join(CRAWLER_DIR, 'output', runId, 'run.log')` — **path traversal attack** reads arbitrary files
2. In `GET /api/runs/:id/data` (line 96): Same path traversal to download arbitrary JSON files

**Fix**: Validate `runId` matches the expected pattern `^\d{8}-\d{6}-[0-9a-f]{4}$` before use.

---

### S2. `server.ts` — Temporary seed file written without cleanup guarantee

**File**: `server.ts` (lines 125-126)  
**Problem**: `seed_${Date.now()}.txt` is written with user-provided URLs directly to the crawler directory. If the server crashes before the `close` event fires, these files accumulate. Also, the URLs are written without sanitization.

---

### S3. No rate limiting on API endpoints

**File**: `server.ts`  
**Problem**: Any client can spam `/api/crawl` (the 409 check only prevents concurrent jobs, not rapid-fire sequential ones) or `/api/tests/run` (which spawns `pytest` subprocesses with no throttle). This is a denial-of-service vector on the host machine.

---

### S4. `config.yaml` exposes placeholder user-agent with `your-email-here`

**File**: `crawler/config.yaml` (line 6)  
**Problem**: `user_agent: "CrawlerPrototype/0.1 (+contact: your-email-here)"` — this is a template placeholder that was never filled in. When crawling, remote servers see this unprofessional user-agent.

## 4. Architecture & Design Concerns

### A1. `fetcher.py` launches a full Chromium browser instance per URL

**File**: `crawler/fetcher.py` (lines 37-38)  
**Problem**: For every URL, `fetch_html` launches a brand new Chromium browser via `p.chromium.launch()`, creates a context, fetches one page, then closes the browser. For a 100-URL crawl, this launches and tears down 100 separate browser processes.

**Impact**:
- Each Chromium launch takes 1-3 seconds of overhead
- Memory spikes on each launch
- Defeats the purpose of Playwright's browser reuse model

**Fix**: Launch the browser once and create isolated contexts per URL (which is what Playwright recommends). Pass the browser instance through the pipeline.

---

### A2. `exporters.py` only exports JSON — README claims CSV support

**File**: `crawler/exporters.py`  
**Problem**: The module only has `export_json()`. The README (line 22) promises `books_extracted_<run_id>.json` or `books_extracted_<run_id>.csv`. The CSV download exists only in the frontend as client-side generation, not as an actual server-side exporter.

**Fix**: Either add `export_csv()` to `exporters.py` or update the README/Documentation to clarify that CSV is only client-side.

---

### A3. `api_bridge.py` opens its own DB connection bypassing `store.py`

**File**: `crawler/api_bridge.py` (lines 10-14)  
**Problem**: `api_bridge.py` has its own `get_db_connection()` function that connects to `crawl.db` using `sqlite3.connect()` directly, bypassing `store.py::get_connection()`. This means:

1. No schema initialization (relies on the DB already being created by a prior crawl)
2. No `PRAGMA foreign_keys = ON`
3. Different connection semantics (uses `row_factory = sqlite3.Row`)
4. Duplicated DB path logic (hardcoded `Path(__file__).parent / "crawl.db"` vs config-driven)

**Fix**: Reuse `store.py::get_connection()` and add a `row_factory` option.

---

### A4. No `conftest.py` for shared test fixtures / `sys.path` setup

**File**: Missing  
**Problem**: The test files import modules like `from urlcheck import ...` directly. This only works if `pytest` is run from the `crawler/` directory (so it is on `sys.path`). There is no `conftest.py` or `pyproject.toml` to configure test discovery or import paths. Running tests from the project root will fail with `ModuleNotFoundError`.

**Fix**: Add a `conftest.py` in `crawler/` or `crawler/tests/` that sets up the path, or add a `pyproject.toml` with `[tool.pytest.ini_options]`.

## 6. Frontend Issues

### F1. 1093-line monolithic `App.tsx`

**File**: `src/App.tsx`  
**Problem**: The entire UI is a single 1093-line React component with no extraction into sub-components. This makes it hard to read, maintain, and test. All state lives in one component (11 `useState` hooks).

**Fix**: Extract into components: `Header`, `UrlInputBar`, `CrawlConsole`, `RecordsExplorer`, `RunHistory`, `TestSuite`, `SpecsPanel`.

---

### F2. `safeJsonFetch` swallows all errors silently

**File**: `src/App.tsx` (lines 83-94)  
**Problem**: `safeJsonFetch` returns `null` for any error — network errors, JSON parse errors, non-JSON responses. The caller never knows what failed or why. This makes debugging nearly impossible.

---

### F3. `fetchStatusAndRuns` has stale closure over `selectedRunId`

**File**: `src/App.tsx` (lines 137-141)  
**Problem**: The `useEffect` that sets up the 3-second polling interval captures `selectedRunId` in a closure but does not include it in the dependency array. This means the initial `selectedRunId` (null) is always used inside the callback.

---

### F4. `useEffect` dependency — `activeJob?.status`

**File**: `src/App.tsx` (line 151)  
**Problem**: `[selectedRunId, activeJob?.status]` as dependencies — optional chaining in dependency arrays is an anti-pattern that can cause missed or extra re-renders.

---

### F5. CSV export missing `final_url` column

**File**: `src/App.tsx` (line 265)  
**Problem**: The CSV headers are hardcoded as `['title', 'price', 'upc', 'availability', 'domain', 'source_url', 'fetched_at']` — missing `final_url`. Records always have `final_url`, so this silently drops data from CSV exports.

## 7. Server Issues

### SV1. `server.ts` — `currentJob` is lost on server restart

**File**: `server.ts` (line 25)  
**Problem**: `currentJob` is an in-memory variable. If the server restarts while a crawl is running, the spawned Python process becomes an orphan (still running), and the UI shows "Ready" even though crawl is in progress.

---

### SV2. `server.ts` — Exit code 1 is incorrectly marked as 'failed'

**File**: `server.ts` (lines 158-163)  
**Problem**: `currentJob.status = code === 0 ? 'completed' : 'failed'` — but `main.py` returns exit code `1` for "completed successfully but with 0 records extracted". This is not a failure. The UI would incorrectly show a failed status for a crawl that ran to completion.

**Fix**: Treat exit codes 0 and 1 as `'completed'`, only 2+ as `'failed'`.

---

### SV3. Express `app.all('/api/*')` catch-all uses deprecated wildcard syntax

**File**: `server.ts` (line 233)  
**Problem**: Express v5 deprecated `app.all('/api/*')` in favor of `app.all('/api/{*splat}')`. While v4 still supports it, this will break on upgrade.

## 9. Configuration & Deployment Issues

### CD1. `requirements.txt` pins exact versions that may not support Python 3.14

**File**: `crawler/requirements.txt`  
**Problem**: Your system runs Python 3.14.7, but requirements pin `playwright==1.49.1`, `lxml==5.3.0`, etc. These specific versions may not have wheels for Python 3.14. This can cause installation failures.

**Fix**: Use minimum version constraints (e.g., `playwright>=1.49`) or test with the exact pinned versions on your Python.

---

### CD2. `config.yaml` uses relative paths — breaks when CWD changes

**File**: `crawler/config.yaml`  
**Problem**: `db_path: crawl.db`, `output_root: output`, `profile: profiles/books.yaml` are all relative. If `main.py` is run from a different working directory, everything breaks.

---

### CD3. `package.json` script `clean` uses `rm -rf` — not cross-platform

**File**: `package.json` (line 11)  
**Problem**: `"clean": "rm -rf dist server.js"` — `rm` does not exist on Windows cmd. Use `rimraf` or PowerShell-compatible syntax.

## 10. Code Quality & Maintainability

### Q1. `fetcher.py` defaults response status to 200 if no response

**File**: `crawler/fetcher.py` (line 60)  
**Problem**: `status = response.status if response else 200` — if `page.goto()` returns `None` (e.g., for `about:blank` or certain redirects), the code assumes success. This masks real failures.

---

### Q2. `robots.py` returns `False` on any non-404 server error

**File**: `crawler/robots.py` (lines 31-33)  
**Problem**: Any server error (500, 502, 503) or timeout when fetching `robots.txt` results in `return False` (disallowed). RFC 9309 recommends treating server errors as temporary "allow" to avoid blocking access due to transient failures.

---

### Q3. `extractors.py` re-parses HTML with BeautifulSoup unnecessarily

**File**: `crawler/extractors.py` (line 52)  
**Problem**: `cleaner.py` already parses HTML with BeautifulSoup, converts back to string, then `extractors.py` parses that string again. Double parsing wastes CPU and memory.

**Fix**: Pass the BeautifulSoup object directly from cleaner to extractor instead of serializing and re-parsing.
